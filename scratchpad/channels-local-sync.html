Channels: full local sync (approach B)

Branch synoet/channels-local-sync, updated 13 November 2026 (reads at ab5d7eced3, writes at 8408dabf70, both with main merged in). Reads, live updates and prewarm are open as four PRs; queued writes are open as a fifth. Not done: a green CI gate on the top of the stack (native version bump needs a ruling, section 1) and removing the REST message path (unblocked, deliberately not built).

What you get. A channel the device holds opens, scrolls back and jumps to a message without asking the server, and stays current by replaying a per-channel change sequence instead of refetching pages. On a slow network a switch to a held channel paints 20 to 32% sooner. On a fast network, on reload and on a cold open it is not faster than today.

What it costs. Every message write now takes a per-channel counter lock, which lowers the ceiling for writes to a single channel from thousands per second to a few hundred, and needs a guard so a flood on one channel cannot starve the rest. Native apps need a new build before they serve channels from the device.

Demo clips. Nine clips of this approach (label b, top of the stack at 8408dabf70, shared recording script, one take each, nothing reported wrong) are in ~/.cache/channels-perf/demos/b/ with a manifest; the channels captain assembles the side-by-side page with main and approach C.

2. How a channel is kept current

open / scroll back / jump
  device holds the window        -> render from the device, no request
  device does not                -> GraphQL page; rows, covered range and sequence saved to the device
  GraphQL fails                  -> today's REST read

push (message_update, now with seq)
  open view                      -> patched from the push itself, as today (no refetch)
  device                         -> one coalesced "changes after N" request, saved by sequence

revisit, reconnect, prewarm      -> "changes after N" from the sequence the device holds
  more than 1,000 behind, or past 30 days of log
                                 -> server says reset: coverage dropped, latest page read fresh

idle                             -> prewarm 40 unread + 20 recent channels; evict channels not opened for 30 days
  • The server gives every committed change to a channel the next number, in commit order. A device that holds number N and asks for changes after N gets everything it missed or is told to start over. It cannot silently miss a change.
  • Opening never waits on the device. While the cache is starting, and for a channel not yet known to be held, the server is asked at the same time and the first answer shows.
  • Two tabs share one engine; the stored sequence only advances from the value the caller read, so one tab cannot skip changes for another.

The captain's three questions.

  1. Does a busy answer or a long offline stretch count toward the queue's drop after 10 failures? No. A failed connection was never counted. A busy answer is now not counted either and is retried with backoff (1 s doubling to 60 s) until the channel lets the write in. A test drives a write already at 9 counted failures through a busy answer and it is kept; the browser run above shows five in a row.
  2. Do several messages queued in one channel arrive in the order typed, once each, across a reload? Yes. Three were typed with sends blocked, the page reloaded, sends unblocked: the three requests went out as 1, 2, 3, and the device and the server both show 1, 2, 3 once each.
  3. What happens to edit, delete and react on a message that is itself still queued? They apply on the device at once (the reaction shows, the text changes, the deleted message disappears) and wait behind the send. On reconnect the requests go send, send, react, edit, delete, and the server ends with the edited, reacted message and without the deleted one. If the send is refused for good, the row is removed, the original draft is restored, the edit behind it is refused too, and both "Failed to send message" and "Failed to update message" show; nothing reaches the server.

Limits of the queue.

  • It is one queue per device, in order. A write to a channel that stays busy holds that person's later writes to every channel behind it until it is let in.
  • A message first delivered more than 30 days after it was typed is refused and rolls back.
  • A write refused after a reload removes its row with no toast, because the screen that would show it is gone.
  • A reply sent offline does not raise the reply count on its root until it is delivered. A thread opened from the server does not show a queued reply until it is delivered.
  • An edit that is sent twice after a lost answer announces the edit twice; the content is the same.
  • The server change must be deployed before the web build that sends these writes; an older server refuses them for good.
  • Agents, bots and API tokens keep posting through REST. Posts anchored to a document also stay on REST.

"Not sent yet" (your call). A send still pending after 5 s shows dimmed with "Not sent yet" beside the time, and returns to normal when delivered. Checked in a browser: no label at 2 s, label and 60% opacity at 6 s, normal after delivery. It shows only in the session that typed the message, not after a reload, and a message grouped under an earlier one is dimmed without the label. A send refused for good behaves as today.

4. The write path: what the counter costs

Who can reach the ceiling, and what everyone else sees

Only a webhook or API caller flooding one channel. People typing cannot. The writers that post to one parent without a person in the loop:

WriterWhat bounds it
Message API and webhooksNo rate limit (the captain ruled none on the webhook); the guard below

Timeline activitiesOne source event at a time per consumer; a batch can append many

The guard. Inside each process, at most 4 writes per parent run at once. The rest wait in memory, before taking a database connection, for up to 2 s, then get a retryable 503. A 5 s database lock timeout covers a holder that stalls. It sits in the shared message write path, keyed by parent, so document comments and every writing process get it. This guard is a cost of decision 2 (ordering by a locked counter). Ordering by snapshot would not need it.

Details the captain asked for

  • What runs under the lock. The counter bump and log insert are the last statements before commit, so the lock is held for those two statements plus the commit. One exception: completing a historical import runs its remaining statements under it.
  • Waiters. They wait in memory, holding no connection. A refused write waited 2.0 s (p50 2,002 ms, p99 2,004 ms). A request cancelled after its SQL started can free its slot early.
  • What a refused sender sees. Web: "Failed to send message" and the draft is restored; there is no automatic retry. Webhook or API: 503 with Retry-After: 1. Agent reply: retried by its existing retry loop. A retry with the same client message id does not create a second message. A webhook retried after an unknown outcome is not deduplicated.
  • Finding it. A span on admission records the parent type, parent id and whether it ran, waited or was refused.

5. Prewarm load at start

Prewarm is capped at 40 unread channels (most recently active first) plus the 20 most recently used. One request at a time, only after the person has left the app alone for 3 s and the browser is idle, re-checked before every channel. A channel already on the device is caught up with changes-after-N, not read again.

8. What a release needs

  1. PR 1 fully deployed before anything reads the sequence. A server still on old code writes messages without logging them, and a device syncing during that window would miss them. So PR 1 goes out in its own deploy, ahead of PRs 2 to 4. PR 5's server side likewise deploys before the web build that sends queued writes.
  2. Migration. One, in PR 1: two new tables (channel_change_counters, channel_change_log). No change to existing tables, no locks on them.
  3. Native build. The device storage schema moves to version 13 and the native cache plugin gains four commands. Desktop and mobile apps need a store build containing PR 3 to serve channels from the device. Older builds answer "unsupported" and keep reading over REST, so the web bundle can ship first. On upgrade the device cache is rebuilt once.
  4. Native version bump: your decision, not made. It is the only thing keeping CI red on the top of the stack. just ios-bump and just android-bump raise each platform's release numbers and, by default, the floor in min-native-build.json: the web bundle then requires that build, people on older builds must update, and the store builds must ship before the web deploy. With --no-min the numbers are bumped without raising the floor, which is enough here, because an older build keeps reading channels over REST. ios-bump reads production release credentials, so I run neither without your approval.
  5. Flag. None new. It follows enable-graphql-soup.
