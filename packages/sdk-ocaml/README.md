# Macro SDK for OCaml

Typed OCaml bindings to Macro's services, for programs whose operations are
read off the compiled program before it runs. Every operation is an OpenAPI
operation of one service, called as a blocking OCaml function through the
SDK proxy, which checks it and forwards it to the service as the caller.

## Operation permissions (`spec/`)

The permission unit is the OpenAPI operation. `spec/` holds the operation
table every other piece reads, and the hand-kept data it is built from
(TypeScript, run with bun from this directory):

| File | What it is |
| --- | --- |
| `spec/permissions.json` | Source of truth: `{"<service>.<operationId>": {"group": "documents", "action": "update"}}` for every operation in `packages/sdk/specs/*.json`. Edited by hand. |
| `spec/renames.json` | An explicit operationId for operations whose own one is not unique in its service, keyed by service and `<METHOD> <path>`. |
| `spec/operations.json` | Generated by `bun spec/build.ts` and committed: `{"operations": [{"name", "service", "operationId", "method", "path", "group", "action", "headers"}]}`, in spec order; `headers` lists the header parameters the operation declares, lowercased (the only program headers the proxy forwards for it). |
| `spec/specs.ts` | Reads the specs and applies the renames; shared by the build and the seed. |
| `spec/seed.ts` | The script that wrote the first `permissions.json`; kept so that classification is reproducible and reviewable. |

An operation's name is `<service>.<operationId>`, with `service` the spec
file's stem and the operationId exactly as the spec spells it (snake_case:
`storage.edit_document`). Cognition repeats `get_state_handler` on
`GET /import/state` and `GET /onboarding`, so `renames.json` names those
`get_import_state` and `get_onboarding_state`. The proper fix is an
explicit `operation_id` on the two handlers' `utoipa::path` attributes
(`crates/import`, `crates/onboarding`), then regenerating the spec copies
and clients and dropping the renames.

`action` is one of `create`, `read`, `update`, `destroy`, `send`; `group`
is a lowercase name, from the SDK's entity directories (`documents`,
`email`, `tasks`, ...) where one fits. `bun spec/build.ts` and
`bun test spec` fail on an operation `permissions.json` does not classify,
an entry that names no operation, an invalid group or action, a duplicate
name `renames.json` does not resolve, a rename that matches no operation,
and (the test) a committed `operations.json` that is out of date.

**Classifying a new operation.** When a spec sync adds an operation, the
test names it. Add an entry to `permissions.json` and rebuild:

- `action` is what the call does, not its HTTP method: `read` changes
  nothing (including POST searches, previews and batch lookups); `create`
  adds something; `update` changes something in place; `destroy` deletes
  or overwrites what can't be got back; `send` reaches other people or
  outside systems (email, invitations, posted messages, notices). When in
  doubt pick the more restrictive one (destroy > send > update > create >
  read).
- `group` is the entity it acts on, named like the SDK's entity directory
  (`packages/sdk/src/entities/<group>/`) when there is one.
- A removed operation leaves a stale entry: delete it.
- Run `bun spec/build.ts` and commit both files.

**Seeding.** `bun spec/seed.ts` follows every SDK method tagged
`@readonly`, `@write`, `@send` or `@destructive` through the type checker
to the generated client calls it reaches. Group is the entity directory
of the call sites; action is read for `@readonly`, send for `@send`,
destroy for `@destructive`, and for `@write` create on POST, update on
PUT/PATCH and destroy on DELETE; a GET, HEAD or known POST read is always
read, and several methods reaching one operation take the most
restrictive action. Operations no tagged method reaches get their action
from the HTTP method and their group from the nearest wrapped path. It
refuses to overwrite `permissions.json` unless given `--force`; after the
first run it isn't needed again, and the hand corrections since live
only in `permissions.json`.

**Why the data lives here.** The specs in `packages/sdk/specs/` are synced
copies of files the services generate, so anything written into them is
overwritten on the next sync. The long-term home is an extension on each
operation (for example `x-macro-permission: {group, action}`) emitted by the services
themselves, at which point `permissions.json` goes away.

## Client (`lib/`, dune library `macro_sdk`)

A typed client generated from the OpenAPI specs (`packages/sdk/specs/*.json`,
OpenAPI 3.1): one module per service, one function per operation, all 913 of
them. A program is one file defining `let main () : Macro.Json.t`. The
duplicate-check example (`test/duplicate_check.ml`) calls the endpoints
behind the TypeScript SDK's `Task.findSimilar` and `tasks.create`:

```ocaml
open Macro.Storage

let main () : Macro.Json.t =
  let title = "Fix login redirect loop" in
  let similar =
    task_similarity_search_handler ~body:(Types.make_task_similarity_search_request ~task_name:title ()) ()
  in
  match List.filter (fun (r : Types.task_similarity_result) -> r.vector_score >= 0.85) similar.results with
  | [] ->
      let created = create_task_handler ~body:(Types.make_create_task_request ~task_name:title ()) () in
      Macro.Json.obj [ ("created", Macro.Json.string created.document_id) ]
  | r :: _ -> Macro.Json.obj [ ("duplicate", Macro.Json.string r.task_id) ]
```

- **Modules.** `Macro.<Service>` per spec file (`storage.json` is
  `Macro.Storage`, `agent-harness.json` `Macro.Agent_harness`), each with
  its schemas in `Macro.<Service>.Types`. A function's name is its
  operationId (after `spec/renames.json`); an OCaml keyword takes a trailing
  `_`. An operationId two services share is told apart by the module.
- **Arguments.** Path parameters are labelled (`~document_id`), in path
  order; query and header parameters are labelled when required and
  optional (`?limit`) otherwise; a JSON body is `~body` (`?body` when the
  spec doesn't require it), typed by its schema. Every function ends with
  `()`. A text, binary or audio body is `~body:string`, sent with the spec's
  content type; a multipart body is a record whose binary fields go as file
  parts.
- **Encoding.** Path values are percent-encoded as one segment; a value the
  proxy would refuse (empty, `.`/`..`, or containing `/`, `\`, `%` or a
  control character) raises `Macro.Error` with code `invalid` before any
  request. Query values are percent-encoded, an array repeats the key, and
  an absent optional argument is left out.
- **Types.** Records for object schemas, each with a `make_<type>`
  constructor (required fields labelled, the rest optional) and
  `<type>_to_json` / `<type>_of_json`. A field that is not required, or is
  nullable, is an `option`; `None` leaves a non-required field out. String
  and integer enums are polymorphic variants (`` `Not_started ``, `` `N1 ``).
  `oneOf` is a variant: tagged when a discriminator or a required constant
  field tells the members apart (the tag field is left out of each member's
  record and written by the encoder), otherwise decoded by trying each member,
  most required fields first; a union whose members can't be told apart is
  `Macro.Json.t` (none today). `allOf` objects are merged; an `allOf` over a
  union distributes over its members. `additionalProperties` is a
  `(string * t) list`. `integer` is `int`, `number` `float`, `format`s
  (dates, uuids) `string`. A schema that allows any value (`{}`, an object
  without properties) is `Macro.Json.t` (`Yojson.Safe.t`).
- **Results** come from the success response's schema: a 2xx with JSON is
  its type; a 204 or a response without content is `unit`; a JSON 2xx next
  to a 204 is an `option`; 2xx responses with different schemas are a
  variant by status (`` `Http_200 of ... | `Http_202 of ... ``); a non-JSON
  body (text, calendar, audio, bytes) is a `string`. Record labels live in
  `Types`, so annotate the value (`fun (r : Types.task_similarity_result) ->`)
  or open the service module. A reply that doesn't match its type raises
  `Macro.Error` with code `decode`.
- **Failures** raise `Macro.Error { code; message; status }`, with the HTTP
  status (0 when there was no reply). A refusal by the proxy itself
  (`x-macro-proxy: refused`) keeps the proxy's code: `blocked`,
  `not_analyzed`, `unknown_operation`, `unauthorized`, `invalid_target`, ...
  A service's error maps its status: `invalid` (400, 422), `unauthorized`
  (401), `forbidden` (403), `not_found` (404, 410), `conflict` (409, 412),
  `rate_limited` (429), `internal` (5xx), `failed` (others), with the
  service's `message` or text. `unreachable` when the proxy can't be reached.
- **Attributes.** Each operation function carries
  `[@@macro.op "<service>.<operationId>"]`, and every other exported value
  `[@@macro.pure]` (codecs and constructors are pure); the analyzer reads
  these. `Macro_runtime` (the transport) carries neither, so programs can't
  use it, and nothing exported sends an arbitrary request.
- **Transport.** A blocking HTTP/1.1 request (Unix sockets and yojson only)
  to `$MACRO_SDK_PROXY_URL/api/<service><path>?<query>` with
  `authorization: Bearer $MACRO_SDK_RUN_TOKEN` (the run token the runner
  registered, never the execution token). The reply is read to its
  Content-Length or last chunk, never to end of file: the proxy keeps
  connections open.
- **Layout.** `lib/macro_<service>.ml(i)` per service and `lib/macro.mli`,
  whose `module Storage : module type of Macro_storage` copies each
  service's signature into `Macro`. Only `macro_runtime.ml`, `macro_json.ml`
  and `macro_error.ml` are written by hand.

## Generator (`generator/`)

```sh
bun generator/generate.ts   # from packages/sdk-ocaml
```

It reads the specs through `spec/specs.ts` (names, with `spec/renames.json`
applied) and groups and actions from `spec/operations.json`, and writes the
client, `lib/operations.json` and the test fixtures
`test/all_operations_calls.ml` and `test/all_operations.json`. All of these
are generated, never committed (`.gitignore`). It emits every operation and
throws on anything it can't emit (an unsupported schema keyword, parameter
style or content type, a name collision) instead of skipping it, then prints
how much fell back to `Macro.Json.t` or `string` and why. It takes about
0.2 s; the client is about 5.6 MB of OCaml and builds cold in about 6 s.

`lib/operations.json`, installed beside the package's `.cmi` files, is
`spec/operations.json` (contract D1) plus each operation's OCaml path:
`{"operations": [{"name": "storage.create_task_handler", "service": "storage", "operationId": "create_task_handler", "method": "POST", "path": "/documents/create_task", "group": "tasks", "action": "create", "headers": [], "ocaml": "Macro.Storage.create_task_handler"}]}`.

**Why our own emitter.** Two OCaml generators were tried against these specs
(November 2026). `ocaml_openapi_generator` 0.17.0 (in nixpkgs) rejects the
specs outright: it reads OpenAPI 3.0.3 and fails on the first 3.1 type array
(`"type": ["string", "null"]`), and its output is Jane Street Async/httpaf
code with its own transport, which the analyzer could not bound. OooapI
(GitHub `XFFS/OooapI`, last change February 2024) is not in nixpkgs or
opam-free, targets OpenAPI 3.0, degrades `oneOf`/`allOf` and recursive
schemas to untyped JSON by its own account, and is hard-wired to Cohttp and
Lwt. Neither can mark each operation `[@@macro.op]` and everything else
`[@@macro.pure]` without post-processing their output, so `emit.ts` (which
keeps the previous generator's naming, records, codecs, variants and
warning-free output) generates the client directly.

## Proxy and permission endpoint

`proxy/` holds the SDK HTTP proxy (`/api/<service><path>`, the only way a
program reaches Macro), the mock permission endpoint (`POST /v1/decide`) and
a fake upstream service for tests. Permissions are per OpenAPI operation,
named `<service>.<operationId>` from `spec/operations.json`. See
[`proxy/README.md`](proxy/README.md) for the CLIs, the order of checks, how
requests are matched to operations, upstreams per environment and curl
examples.

Binding each run to its analysis:

- `POST /v1/executions`, `authorization: Bearer <execution token>`, body
  `{"operations": ["storage.edit_document", ...]}` → `200 {"token": "<run token>"}`,
  a fresh random token per run. The runner calls it with the analyzed list
  after the permission check, and gives the program only the run token, as
  `MACRO_SDK_RUN_TOKEN`.
- `/api/...` accepts only a run token. The execution token, or any unknown
  token, answers `401 unauthorized`, so a program cannot skip registration.
- An operation outside the run's set answers
  `403 {"error":{"code":"not_analyzed",...}}` before the permission endpoint
  is asked. Inside the set, the permission endpoint is still asked on every
  call. Every response the proxy produces itself carries
  `x-macro-proxy: refused`; a service's own answers pass through unchanged.

## Building and testing

Toolchain: `shell.nix` (OCaml 5.4, dune, findlib, yojson, bun, curl). The
client comes first (it is not committed); from the repository root, after
`bun install --frozen-lockfile` at the root:

```sh
nix-shell packages/sdk-ocaml/shell.nix --run 'cd packages/sdk-ocaml && bun generator/generate.ts && dune build @install && dune test && bun test generator spec'
```

The client's checks:

- `dune test`: `check_interface` reads the compiled `Macro` interface and
  checks one `[@@macro.op]` value per `operations.json` entry at its path,
  every other value `[@@macro.pure]`. `all_operations` calls every operation
  twice (required arguments only, then all of them) against a fake proxy,
  checks the method, encoded path, query, header parameters, run token,
  content type and body against `test/all_operations.json`, and decodes a
  reply generated from the response schema (first members of unions, then
  last). `test_duplicate_check` runs the duplicate-check program against a
  fake proxy that keeps connections open: its requests and result, a chunked
  reply, proxy refusals, service errors, a decode error, no proxy, and a path
  value with a slash failing before any request.
- `bun test generator`: `lib/operations.json` has one entry per operation in
  the specs with spec/operations.json's fields; every sample target passes
  the proxy's own target checks and routes to its operation
  (`proxy/src/router.ts`); every sample body and reply validates against its
  schema.

`dune build @install` installs `macro_sdk` as a findlib package with
`operations.json` beside its `.cmi` files, which the analyzer and runner read.

## Analyzer: `macro-sdk-analyze`

```sh
macro-sdk-analyze prog.ml
# {"ok":true,"operations":[{"name":"storage.create_task_handler","group":"tasks","action":"create"}, ...]}
# {"ok":false,"errors":[{"message":"`Obj.magic` belongs to Obj, which programs may not use","line":4}]}
```

Exit 0 when accepted, 1 when refused, 2 when the SDK can't be found.

It type-checks the program in-process with compiler-libs, with only the SDK
directory visible and the SDK's dependencies (yojson, unix, the transport's
HTTP client) hidden with `-H`, so the type checker can read them but the
program cannot name them. It then walks the typed tree and records every
value whose declaration carries `[@@macro.op "<operation>"]`. Every operation
named anywhere in the file counts, reachable from `main` or not: the list is
what the program *may* call, not what one run *will* call.

**Soundness claim.** A program the analyzer accepts can only cause SDK calls
that are in its list. The argument: the only code that can talk to the proxy
is the SDK's transport; a program can reach it only by naming an SDK value,
by naming a module that contains one, or by escaping the language. The
analyzer judges every named value and every module used as a value, and
refuses the escapes below.

What it refuses, and why:

| Refused | Why |
| --- | --- |
| `external` declarations, in structures or signatures | they bind any C or compiler primitive, `%identity` included |
| Any value of the SDK library with neither `[@@macro.op]` nor `[@@macro.pure]` | that is the transport and other internals |
| An SDK module used as a value (functor argument, `include`, first-class module, signature constraint, `module rec`, alias nested in a structure) when its contents include an unmarked value | the module would carry the transport in without naming it |
| Anything in the standard library outside the allow-list in `analyzer/lib/policy.ml`: `Obj`, `Marshal`, `Sys`, `In_channel`, `Out_channel`, `Effect`, `Domain`, `Mutex`, `Callback`, `Gc`, `Random`, `Filename`, `Scanf`, `Lexing`, `Bigarray`, `Weak`, `Camlinternal*`, `Std_exit`, ... | type-unsafe casts, I/O, processes, concurrency; a new Stdlib module is refused until reviewed |
| Stdlib channels and I/O functions (`print_*`, `read_*`, `open_*`, `stdout`, `exit`, `at_exit`, `Printf.printf`, `Format.std_formatter`, ...) | I/O; formatting is allowed only into strings and buffers |
| Every `unsafe_*` function (`Array.unsafe_get`, `Bytes.unsafe_set`, `Float.Array.unsafe_get`, ...) | out-of-bounds memory access could forge a call |
| A Stdlib module used as a value whose contents include a refused function (`include String`, `F (Printf)` where `F` asks for `printf`) | same as the SDK case: the functor would reach it unnamed |
| `Unix`, `Thread`, `Dynlink`, `Yojson`, the HTTP client | not on the search path (the compiler's automatic `+unix`/`+threads`/`+dynlink` include is switched off), so "Unbound module" |
| Classes from outside the program | none are allowed; local classes and objects are fine |
| Attributes other than `warning`, `warnerror`, `doc`, `text`, `alert`, `deprecated`, `deprecated_mutable`, `inline`, `inlined`, `tailcall`, `unrolled`, `specialise`, `specialised`, `immediate`, `unboxed`, `boxed`, `warn_on_literal_pattern` (with or without `ocaml.`) | others are ppx input or change compilation; `[@@macro.op]` written by a program is refused too |
| Extension nodes (`[%foo]`) | ppx input |
| A file without `let main () : Macro.Json.t` | the runner calls it |
| A type named `__macro_sdk_main_result` | it names main's expected type; redefining it would let a wrong `main` through |

What is fine: `open Macro`, local opens, `let open`, toplevel and `let module`
aliases (each use is checked through the alias), passing an operation as a
function value, partial application, shadowing `Macro` with a local module
(its functions are the program's own), local modules named like SDK modules,
functors, first-class modules and objects (an SDK module given to a functor is
checked through the functor's parameter, so `F (Macro.Document)` counts only
what `F` asks for), `let rec`, binding operators, toplevel effects outside
`main` (their operations count), `Map.Make (String)` and the other pure
Stdlib functors.

Assumptions the SDK must keep: every operation is a value marked
`[@@macro.op]`; nothing marked `[@@macro.pure]` makes a call; no SDK value
returns a closure or object that makes calls (handles are data). Known limit:
a bug in the OCaml type checker itself would break the argument.

The analyzer never searches the directory it is started from
(`Clflags.no_cwd`), so a stray `.cmi` there cannot stand in for the SDK or
the standard library.

`analyzer/test/` runs 81 programs, plus a check that the current directory is not searched, against the test SDK
(`analyzer/test/mini_sdk`: `Macro.Tasks.find_similar`, `Macro.Tasks.create`,
`Macro.Document.content` and `Macro.Document.delete`, marked as the storage
operations `task_similarity_search_handler`, `create_task_handler`,
`get_document` and `delete_document`; `Macro.Json` helpers; and an unmarked
`Mini_transport` that sends D3 requests): `dune test`.

## Runner: `macro-sdk-run`

```sh
MACRO_SDK_PROXY_URL=http://127.0.0.1:8787 \
MACRO_SDK_PERMISSIONS_URL=http://127.0.0.1:8788 \
MACRO_SDK_EXECUTION_TOKEN=<execution token> \
  macro-sdk-run prog.ml
# stderr: macro-sdk-run: operations: storage.create_task_handler, storage.task_similarity_search_handler
# stdout: {"result": ...}
```

1. Analyze the file (read once; the same bytes are compiled).
2. `POST $MACRO_SDK_PERMISSIONS_URL/v1/decide` with the operation names. Any
   answer but `allow` counts as blocked.
3. If anything is blocked, print
   `{"error":{"code":"blocked","message":...,"methods":[...]}}` and exit 3
   without compiling or running.
4. Compile the program as `user_program.ml` with the analyzer's exact search
   path (`OCAMLPARAM` is dropped) and link it with a generated entry point that
   calls `main ()`.
5. Register the run: `POST $MACRO_SDK_PROXY_URL/v1/executions` with the
   execution token and the analyzed operations; the proxy answers with a run
   token that can call only those operations.
6. Run the program in a temporary directory with only `MACRO_SDK_PROXY_URL`
   and `MACRO_SDK_RUN_TOKEN` in its environment; it never sees the execution
   token.
   The entry point prints `{"result": <main's value>}`, or
   `{"error":{"code","message"}}` when `main` raises.

| Exit | Meaning |
| --- | --- |
| 0 | ran; stdout is `{"result": ...}` |
| 1 | the analyzer refused the program; stdout is its JSON |
| 2 | setup failure: environment, permission endpoint, compiler, run registration |
| 3 | an operation is blocked; nothing was compiled or run |
| 4 | the program raised (`Macro.Error` keeps its code, e.g. `blocked` from the proxy) |

There is no time limit on the program yet.

## End-to-end check: `e2e/run.sh`

```sh
packages/sdk-ocaml/e2e/run.sh   # against the generated macro_sdk
```

It enters the Nix shell if needed, installs the workspace packages when
missing, regenerates the client every time, builds, and starts two permission endpoints (`e2e/rules-strict.json` allows reads and
task creation and blocks `@destroy`, `e2e/rules-permissive.json` allows
everything), a fake storage service (`proxy/src/fake-upstream.ts` with
`e2e/upstream.json`) and the proxy, all on the installed `operations.json`;
the proxy checks the strict endpoint and gets the execution token and a
placeholder credential through its environment. Then it asserts:

1. `test/duplicate_check.ml` (search similar tasks, create only when none is
   similar) is allowed, runs through the proxy, and returns the created task;
   the fake service saw the search and the create.
2. `e2e/programs/delete_document.ml` (`storage.delete_document`, action
   `destroy`) is refused before it runs (exit 3, the proxy logs no call).
3. The same program, allowed by the runner's permissive endpoint, fails at
   call time: the proxy asks the strict endpoint and answers 403 `blocked`,
   which `main` raises as `Macro.Error`, and nothing reaches the service; a
   direct `curl` with a run token that lists `storage.delete_document` gets
   the same 403 with `x-macro-proxy: refused`. This is the policy checked on
   every call.
4. A call the analysis did not approve: a run registered for
   `storage.task_similarity_search_handler` only, used directly with `curl`
   for task creation (which the strict policy allows), gets 403
   `not_analyzed`; the same token still searches; the execution token gets
   401.
