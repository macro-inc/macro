Email Focus · linked inboxes

A linked inbox follows its primary user's Focus flag

PR #{{PR_NUMBER}} head {{HEAD}} base main e22fa6483f5 code tour (tailnet) 2026-11-19

What it does

Focus only ran for a user's own inbox. When someone links a mailbox whose address has its own Macro account, the inbox stays that account's, and the Focus worker asked only that account's flag. The person who linked it saw the inbox in their Focus tab, but its mail was never classified.

Now an inbox is classified while anyone whose Focus tab shows it has the enable-email-focus flag: its owner, or a user it is linked to through macro_user_links. A linked inbox whose primary user is not on the flag is not classified unless its own owner or another user it is linked to has the flag. Taking a primary user off the flag stops every inbox only they kept in.

Where the check changed

Walkthrough

Data. FocusInbox and FocusInboxOwner gain delegates, the users other than the owner the inbox is linked to. The three reads that produce them (thread_inbox, inboxes_with_focus, syncing_inboxes in crates/email/src/outbound/focus_pg.rs) each add the same correlated array:

ARRAY(
    SELECT mul.primary_macro_id
    FROM macro_user_links mul
    WHERE mul.link_id = el.id AND mul.primary_macro_id <> el.macro_id
) AS "delegates!"

Rust sorts and deduplicates the ids (one user can reach a mailbox through more than one account), and leaves out a malformed id with a warning that names the link, never the id, so one bad row cannot fail a read of many inboxes.

Rule. FocusService::is_enrolled in crates/email/src/domain/focus/service.rs asks the owner first, then each linked user:

for reader in std::iter::once(owner).chain(delegates) {
    match self.enrollment.is_enrolled(reader).await {
        Ok(true) => { enrolled = true; break; }
        Ok(false) => {}
        Err(error) => { unknown.get_or_insert(error); }
    }
}
if !enrolled && let Some(error) = unknown {
    return Err(error);
}

The remembered set of enrolled inboxes now keeps each inbox's linked users, and the hourly sweep prefers the ones it just read over the remembered ones, so an unlinked inbox drops out at the next sweep. FlagEnrollment in the worker is unchanged in behaviour: it already answered for any user id.

Decisions

  • The owner still counts. The brief said the primary user's flag decides. A macro_user_links edge exists only when the address has a Macro account of its own (or is a shared mailbox's own user), so going by the primary alone would turn off that account's own Focus. Asking the owner first also keeps an account's own inbox at one flag check.
  • Yes wins; an error only blocks when nobody says yes. An unreadable owner does not hold back an enrolled linked user, and a failed read never enrolls anyone.
  • One index probe per inbox. For the whole-set look, a hash join of all edges (100–175 ms) and a pre-aggregated join (170–195 ms) were no cheaper than the probe (190–315 ms), and a GROUP BY form spilled 9 MB to disk under stale statistics. Deduplicating in Rust instead of in SQL took the probe from about 275 ms to 190 ms.
  • No statement timeout. None of the reads depends on one tenant's data; the two whole-set reads run from single background loops that wait for each other, and the worker runs as one replica.

Review fixes

CodeRabbit found two places where a remembered list of linked users could go stale. Both are fixed in {{FIX}}.

  • The sweep no longer settles a thread it found out of the rollout. The sweep admits an inbox it saw enrolled earlier, with the linked users it read then. When a thread's own read finds the inbox out (the user was unlinked since), the thread was stored as checked at its latest mail, so after a re-link neither the sweep nor a backfill looked at it again until new mail came. Now NotEnabled is never settled, the sweep stops walking that inbox and gives the unstarted threads back to its budget, and the report counts it as inboxes_left.
  • A backfill pass that finds the inbox out is not counted as filled. A queued pass kept the linked users of the look that queued it, and a pass that found the inbox out (at the start, or partway) still counted as done, so the inbox could be marked filled without being filled. Now each look gives every waiting inbox the linked users it just read, and such a pass is dropped, so the next look queues the inbox again if it is in.

Not proven

  • The web app was not driven in a browser. No web code changed; the scenario reads Home's list and a thread's Focus with the GraphQL queries the web app sends. The browser suite's stack server cannot start the Focus worker.
  • The production flag's conditions were not read or changed. Both the worker test and the scenario serve flag definitions locally and use the worker's real local evaluation.
  • Production row counts were not measured; the seed is assumed larger than production for mailboxes. The every-minute look grows linearly with connected mailboxes.
  • A primary user losing the flag mid-run (the five-minute flag refresh) is covered by service fakes and by the worker test with the flag off, not by an end-to-end run. Outlook links (delegate and rehome) are covered by the database read tests, not by a scenario.

Noticed, not changed

  • Classification is profiled and metered against the inbox's owner, not the linked user whose flag enrolled it.
  • The gateway push reads the same edges again for every push; it could take the linked users the service already has.
  • A backfill checks the rollout once, when it starts, so one under way finishes its pass after the user who enrolled the inbox leaves. Owners had the same behaviour.
