# contacts

## What it is

Part of Contacts: a hexagonal service tracking who each user knows, built
from message/call activity and explicit relationships, exposed over HTTP
and kept in sync via the connection gateway.

## Start here

- `src/domain/service.rs`: the contacts use cases (`domain::service`), including bounded ID pages through `ContactsPageService`; the deployed full-list API is unchanged.
- `src/domain/service/directory.rs`: bounded enrichment, search, and membership-first lookup. Search is ID-ordered, not ranked: at most four 500-row batches are named per request, and empty results may have a continuation. Every returned contact carries `lists`, read once per call from `ContactListReader::contact_lists` for the returned ids only (for search, the matches), whichever store chose them, so a contact only the legacy graph returns has none.
- `src/domain/list_reads.rs`: the per-viewer read cutover. `FlaggedContactReads` serves `ContactsPageService` (pages, lookups), `ContactsService` (`query_contacts`, the full listing paged 500 at a time; `query_contacts_among`, requested ids looked up 500 at a time — the default filters the full listing), `PeopleSearchService` (the list-aware search; a legacy search's matches get their lists from `contact_lists`) and `CorrespondentsService` (the list-aware path returns only inbox contacts; the legacy one the whole directory) from the legacy graph or `ContactListReader`, by the PostHog flag `contacts-list-reads` loaded for the viewer. Each viewer's answer is kept 5 minutes per process; a failed or missing load means the legacy graph and is kept too. `ContactListReads::optional(None)` (a deployment without a PostHog key) means the legacy graph for everyone. Evaluated in every environment, local included (target `environment = local` to try it). Composed by DSS (GraphQL contacts, `databases_sql` people, the SSE contact audience), `contacts_service` (`GET /contacts`, `GET /contacts/search`; optional `POSTHOG_API_KEY`), `authentication_service` (the team domain notice's correspondents, through `teams`' `ContactsColleagueDirectory`) and `ai_tools` (agents' `macro.people`). The picture fan-out has no viewer and notifies both audiences.
- `src/domain/models/contact.rs`: viewer/person-derived normalized identity and nullable resolved names; email fallback stays with the consuming surface. `contact/identity-fixtures.json` freezes the UUIDv5 contract for viewer-scoped point reads; keep it stable for clients.
- `src/outbound/names.rs`: `directory-names` feature, reusing the existing user-name owner's profile-over-address-book query without duplicating SQL.
- `src/domain/models/page.rs`: page sizes (default 100, maximum 500) and original per-row positions, distinct from canonicalized user IDs. Short/empty pages may still have continuations.
- `src/domain/models/query.rs`: 512-byte normalized subsequence searches (including the local-part label fallback plus email), exact/first-name reference predicates applied before limiting and at most 500 raw lookup IDs, deduplicated without reordering; empty lookup never means all contacts.
- `src/outbound/repository/page.rs`: indexed paging of both graph directions and self, plus exact lookups through `lookup.sql`. Legacy reads are one-directional where the directed lists can tell: `page.sql`, `lookup.sql`, `contacts.sql` (the full listing) and `people_search.sql` hide a peer when the peer's inbox or `invited` row names the viewer and no list or inbox row of the viewer's (nor the team) names the peer. Pages return hidden rows flagged so the cursor advances past them, so a page may be short. Edges no list explains (written while `contacts-list-writes` was off) stay visible both ways until the viewer moves to `contacts-list-reads`. Match peers with `lower(... COLLATE "C")` and the strict `macro|` prefix predicate using the two scoped expression indexes; keep raw viewer equality and raw page cursors unchanged. Membership is bounded per input key before names; preserve the LATERAL limit and both custom/generic 100k-row plan regressions. Deploy migrations `20261105044718` and `20261105044750` before the lookup query.
- `src/outbound/repository/people_search.sql` (`GET /contacts/search` for legacy viewers, `PeopleSearchService`, models in `src/domain/models/people.rs`; `search_people_with` in `service.rs` holds the too-short and limit checks both searches share): one ranked query over the viewer's edges, self, and current team (`team_user`); teammates first, then name/email prefix, then byte-ordered name/email. Matches email and Macro profile names only (address-book labels name results but are not searched). Trimmed queries under 2 chars read nothing; limit default 20, capped at 50; 5 s statement timeout. Cost is ~6 index probes per candidate ("User" + `macro_user_info`): ~94k buffer hits / ~100 ms for 15k contacts. Keep candidate ids in the default collation or the joins lose their indexes.
- `lookup_contact_ids` (through DSS's `FlaggedContactReads`, so it follows the subscriber's flag) also backs the webhook SSE contact audience (`document_storage_service` `stream_contacts` adapter): one exact lookup of the event's user in the subscriber's directory per subscriber per event.
- `src/domain/models/list.rs`: the directed, list-aware directory (tables `contact_list_members` and `contact_inbox_members`, replacing `contacts_connections`). `ContactList` keys (`teammates` is computed at read time, never stored; `interacted`, `invited`, `gmail`, `outlook`) and `InboxSource` (owner, `email_links` id, provider).
- `ContactListIngress` (`src/domain/ports.rs`, implemented by `SqsContactsIngress`) is the producer API: `record_interactions` (mutual, chunked to 10 users × 500 peers per message), `record_inbox_contacts` (directed, 500 per message), `directory_changed` (notify only; more than 500 changed ids are sent as unknown) and `user_deleted`. Each publishes a `DirectoryChange` (`src/domain/models/messages.rs`, tagged by `type`); `ContactsMessage` tries it before the untagged legacy shapes.
- `src/domain/list_writes.rs`: the rollout gate for list-aware messages. Producers wrap their ingress in `ListWritesGate`, whose `ContactListIngress` calls send nothing until the global PostHog flag `contacts-list-writes` is on (service context `contacts-list-writes`, read at most once a minute; on in a local stack, off without a PostHog key or when a read fails). `ContactsIngress` (legacy messages) passes through ungated. Workers released before `DirectoryChange` delete it as unparseable, so turn the flag on only once every contacts worker runs a release that reads it.
- `src/outbound/repository/lists.rs` (`ContactListRepository`): idempotent `INSERT … ON CONFLICT DO NOTHING RETURNING` writes that report only added rows; inbox rows are skipped once the `email_links` row is gone. `process_change` in `src/domain/service.rs` notifies only owners whose rows were added, naming those contacts as `changed` (`ContactsInvalidation`, at most 500; a removal is sent unknown). `InboxContacts` also writes the legacy `contacts_connections` edge first, so the old read path stays complete and a retry after a failed write still notifies. `POST /contacts` (referral invite, `ContactsService::invite_contact`, synchronous and not gated) writes the legacy edge and then one directed `invited` row caller → invitee (`lists/record_invite.sql`), notifying only the caller (on every call, so a retry after a failed notification still delivers it). Deletion ordering: interactions skip any id with no `"User"` row (matched by id or, for a legacy id stored with capitals, by `lower(email)`; rows always name the canonical id), and after the insert commits `drop_deleted_accounts` checks the ids again (`lists/missing_profiles.sql`) and drops the lists of any whose profile was deleted meanwhile. `delete_user_lists` fails while the profile still exists (matched the same way); account deletion queues `UserDeleted` just before deleting the profile, so the next receive normally finds it gone. A message refused 5 times moves to `contacts-dlq-<stack>` with no replay; that happens only when the profile was never deleted, and a retried account deletion queues it again. Inbox and invited rows may name people with no account, so they are not guarded; a later sync can list a deleted user's address again as an email contact.
- `src/outbound/repository/directory.rs` (`ContactListReader`, models in `src/domain/models/listed.rs`; keys parse with `ContactList`'s `FromStr`, unknown keys are skipped): reads of the list-aware directory, called through `FlaggedContactReads` (pages, lookups) and `ContactsDirectoryService` (`contact_lists` for every viewer). A directory is the owner's `contact_list_members` and `contact_inbox_members` rows, the current team (`team_user`, ids folded with `lower(... COLLATE "C")`; a legacy mixed-case row for the viewer is found through `"User"` `lower(email)`) and self; the audience is the reverse, through the `(contact_user_id, user_id)` indexes. Pages keyset on the C-collated id with `LIMIT` per branch; lookups and list keys take at most 500 ids, two point reads each. The team roster is read whole on every read (no index orders it). The viewer has no lists of their own. 5 s statement timeout. `directory/test/plans.rs` pins custom and generic plans at 100k rows. `search_listed_people` (`directory/people_search.sql`) ranks by list group (teammates, the viewer included when on a team; `interacted`/`invited`; `gmail`/`outlook`; anyone else), then prefix, then name, and returns each match's lists; like the legacy search it reads the whole directory and probes "User" and `macro_user_info` per candidate (~600k buffer hits / ~650 ms for 75k contacts against 500k accounts, the same as the legacy search on that directory), so it is not in the plan test, whose small "User" table makes the planner hash-join it. `inbox_contacts` is one range read of the owner's `contact_inbox_members` rows (~500 buffers for 50k).
- `src/domain/backfill.rs` (`DirectoryBackfill`, driven by `contacts_service`'s `contacts_backfill` bin): fills `interacted`, `gmail` and `outlook` from channels, the April 2026 `contacts_backfill_outbox` snapshot, DMs with a person's message and legacy edges an owner's inbox explains, through `ContactListRepository`, and first sweeps rows left by deleted accounts (`OrphanedListRows`: list rows whose owner has no "User" row, `interacted` rows whose contact has none; an id matches an account by id or address); `audit` classifies every legacy edge direction (`backfill/audit.rs`) and projects `interacted` rows by channel size. `backfill/channels.rs` holds every channel's Macro members in memory so the audit never joins per edge. Reads are keyset pages behind `LegacyDirectorySource` (`src/outbound/repository/backfill/*.sql`).
- `src/domain/ports.rs`: the traits `inbound`/`outbound` implement.
- `src/inbound/http.rs`: HTTP handlers, router, DTOs, swagger.
- `src/inbound/worker.rs`: SQS worker that ingests contact-affecting events. It deletes a message only after it is processed; an unparseable one is left for the queue's redrive policy to move to `contacts-dlq-<stack>` after 5 receives. The local queue has no DLQ, so there it redelivers every 30 s. Each message is its own root span, `contacts.worker.process_message`, parented on the `traceparent` message attribute that `SqsContactsQueue` adds when it publishes (`src/trace_context.rs`); the poll loop has no span. Contacts spans and logs record counts, kinds, and message ids, never user ids (they are emails).
- `src/domain/service/picture_fanout.rs`, `src/inbound/user_picture_consumer.rs`, `src/outbound/picture_gateway.rs` (`picture-fanout` feature): `macro.users` `user.picture_changed` → pages the user's legacy neighbors (`contact_id_page`) and then everyone who has the user in their list-aware directory (`audience_page`), ≤500 per page, never the full list, and sends gateway message `user_picture_changed` `{"user_id"}` to each page (self included). While `contacts-list-reads` ramps nothing says which store a recipient reads, so both audiences are notified; someone in both gets it twice. The consumer (group `contacts-user-picture`) batches records for 250ms/100 records and fans out once per user per batch; failures retry 3× then are logged and skipped (realtime is best-effort). Hosted in `document_storage_service`; Kafka IAM is cluster-wide, so no infra change.
- `ContactsMessage::Disconnections` (`ContactsIngress::enqueue_contact_disconnections`, ungated, 500 per message) deletes legacy edges in either order and notifies both ends as unknown; teams sends it when a membership ends. Workers released before it leave it for the DLQ.
- `src/outbound/repository.rs`: Postgres adapter; `src/outbound/gateway.rs`
  notifies the connection gateway of graph changes: `contacts_invalidation`
  with `{"changed": [...]}` when the contacts to re-read are known, `{}` otherwise.
  For the legacy `Nodes`/`Connections` messages, each user is told the other
  end of each of their connections (≤500, ordered by id), which the web leader
  tab re-reads at once.

## Scope

- Owns: the contact graph (who a user has an explicit or inferred
  relationship with) and its HTTP/queue surface.
- Not here: CRM companies/contacts (external organizations) → `crates/crm`;
  connection-level presence/relay → `crates/connection_gateway_client`.

## Boundaries

- Depends on: `macro_authorization` (axum feature), `rate_limit`, `sqs_worker`,
  `macro_user_id`, `feature_flags` and `macro_env` (the list-writes gate and the list-reads flag).
- Used by: `graphql_contacts` (paged directory reads), `contacts_service` (composition root), `teams` (legacy edges,
  `directory_changed` on membership changes, and `CorrespondentsService` for the domain notice), `channels`, `ai_tools`, `databases_sql`; also linked into
  `document_storage_service`, `authentication_service`, `email_service`,
  `agent_harness_service`.

## Recipes

- Add an HTTP endpoint: `src/domain/ports.rs` (port method) →
  `src/domain/service.rs` → `src/inbound/http.rs` (handler + router + swagger).
- Change what triggers a contact update: `src/inbound/worker.rs` (SQS message
  parsing) → `src/domain/service.rs`.
- Add a repository query: `src/outbound/repository.rs` → its `test.rs`.

## Checks

- `cargo test -p contacts --all-features -- --test-threads=2` (`SQLX_OFFLINE` unset; `directory-names` covers name precedence/account isolation; the `outbound`/`default`
  features need a local MacroDB — see `.agents/rules/rust/guardrails.md`).

- `cargo test -p contacts --all-features '::case_lookup::' -- --test-threads=2 --nocapture`: canonical point lookup matches legacy-case IDs exposed by paging, rejects invalid marker/Unicode aliases and other viewers, and seeks the new expression indexes at 100k under custom/generic plans. Directory-name tests also preserve viewer-private labels and normalized identities.
