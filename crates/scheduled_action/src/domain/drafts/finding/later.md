A routine that does something once, later, for each item a run finds or an event brings (a reminder the day before each task is due, a follow-up two days after a channel is created) defines that work once, as a sub-routine in its `subRoutines`, and a code step schedules a copy of it for each item: `await macro.routines.schedule('remind_before_due', { trigger: { type: 'once', at }, inputs: { taskId: task.id }, key: task.id })`, on the step's own `macro` (one passed to a helper typed with the SDK's `Macro` can't schedule). A sub-routine is `{ name, title, inputs, steps }`: `name` is how the code schedules it (lowercase letters, digits and underscores, starting with a letter, at most 32), `title` says what each copy does in a few words, `inputs` are the values each copy is given (`{ type: 'text', name: 'taskId', label: 'Task' }`; `number` and `boolean` too; a name is a lowercase letter then letters or digits, at most 32, so `taskId`, never `task_id`), and its steps follow the rules for steps here. `schedule` passes every input the sub-routine declares, by its exact name, as a string, number or boolean as its type says, and no other. Its code steps read the inputs as `inputs.taskId` (`export async function main({ macro, inputs }: StepContext)`), and its Ask AI step is given them as data. Every copy runs the sub-routine as the routine holds it when the copy runs, so the owner reviews and edits it once, here. Give each copy a `{type: 'once', at}` trigger, never a `cron` one, and a `key` naming the item, so a later run updates that copy instead of adding another; keys are shared by all of the routine's sub-routines, so a routine with more than one prefixes each key with the sub-routine's name (`remind:${task.id}`). `at` is an ISO 8601 time with its offset (`date.toISOString()`). The code works `at` out from the item and `run.at` as a time on the owner's clock in `run.timezone` (9am the day before is 9am there, not in UTC), and skips an item whose time has passed: a past `at` runs as soon as it is scheduled. To tell the owner, the sub-routine ends with its own Ask AI step, whose instructions say what to tell them about the item its inputs name; so the scheduling is never the routine's Ask AI step's to do. Work that repeats until something happens (a check every morning until a thread is answered, a weekly check on each new task while it is open) is not a sub-routine, even when an event brings the item: it is a routine on that schedule looking for what is still open. A run can schedule a new sub-routine only while its routine has fewer than 50 active ones: its copies and any other routine its runs made, counted together, a one-time one until it fires at its time (even if that run then fails); scheduling a new one at 50 is refused, and rescheduling one by its key adds none. All its sub-routines' code steps, plus the routine's own or its largest sub-routine's, whichever has more, stay within 40, so keep each to a few. Only the routine's runs schedule copies, never your program; the check type-checks the sub-routine's steps, and the `schedule` calls against its name and inputs. The scheduling step's `sentence` says what it schedules and when.
