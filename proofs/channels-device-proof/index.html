The stale engine, and what it voids

  • my faultEvery bundle I staged from 15 November 12:50 on carried a cache engine built at that time. B's commit 22c528f5f7 (13:30 that day) added the lease owner, generation and expiry to what the engine reports about queued writes, and the web code reads them to free a write left by a page that is gone. bun run build does not rebuild the engine, and just ensure-cache-wasm rebuilds it only when the crate's version changes. So new web code ran on an old engine: the release returned early and a reloaded page's writes waited the queue's five minutes.
  • checkedI confirmed the owner's diagnosis before acting on it. My engine file was dated 15 November 12:50 and did not contain the lease fields; the rebuilt one (version 0.6.55) does.
  • voidThe columns for c060e4667f and 63e04cd9b1 are void, with the whole-suite runs and break proofs made on them, and so is what I wrote against the owner about WRT-04, MSG-13 and CMP-13. The column for 8408dabf70 stands: that engine was built from that head's sources.
  • beforeOn the stale engine at 04adb57188, with six copies of each test in five whole-suite runs: WRT-04 was late in 24 of 30, CMP-13 in 8 of 30, MSG-13 in 6 of 30, every one arriving about 300 s after.
  • afterOn the fresh engine at 94876dc650, same runs: 30 of 30 each. No message took longer than its usual wait (40 s for WRT-04, 15 s for the others). The queue logged the release of a lease left by a page that was gone on 51 pages.
  • unprovenThe owner's newer fix for a lease the same page holds without sending (lease-unrouted) never fired in 850 flag-on test runs with the console captured. Nothing here shows it is needed or that it works.
  • guardMy build and run scripts now refuse a bundle whose engine is older than the last commit to the engine's crates, and the suite's guide says to rebuild the engine before building a bundle.
