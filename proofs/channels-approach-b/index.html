Channels on the device: approach B

How channels open from the device cache, stay current without refetching, and keep a person's own writes through an outage. What is built, how each piece works, what the flag does and does not cover, and what is still open.

The idea in one paragraph

Today a channel is read over REST every time it is opened. Nothing is kept on the device, so each open, reload and switch waits on the network, and nothing shows offline. Approach B keeps channel messages in the same device cache that already holds the rest of the app's GraphQL data. Three things make that safe:

A sequence per channel

Every committed change to a channel gets the next number. A device that holds a channel at number N can ask "what changed after N" and get a complete, ordered answer, or be told to start over. This is what "never out of date" rests on.

An index that knows what it holds

The device records which stretches of a channel are complete. It answers a read only when the requested window lies inside one of those stretches. Otherwise it reports a miss and the server is asked.

A durable queue for writes

A send, edit, delete or reaction is stored on the device before it is sent. It survives a reload and an outage, is delivered in the order written, and cannot post twice.

REST is not removed. It remains the fallback for every read that fails, for older native builds, for anyone without the device cache, and for everything when the flag is off.

Layer 1: the change sequence

Two new tables, with no foreign keys and nothing added to existing tables:

  • channel_change_counters: one row per channel holding its current sequence number.
  • channel_change_log: one row per change, keyed by channel and sequence. A row is a message change, an activity change, or a reset marker. Rows are never updated.
message / reaction / thread / activity / call-status write
  -> admission for this channel (in memory, before a database connection is taken)
  -> transaction: the write itself
  -> last statement: bump the channel's counter, insert one log row
  -> commit        (the counter row stays locked from the bump to the commit)
  -> push to open clients, carrying the committed sequence

Why the counter is locked last

Because the counter row is locked as the final statement and held until commit, sequence order equals commit order within a channel. A reader can never see change N+1 while N is still invisible. That is the property the device depends on: "everything after N" is always complete. You confirmed on 2026-11-16 that this design stays.

The cost, and the guard against it

Writers to one channel now queue on one row. A flood of writes to a single channel could otherwise hold database connections while waiting. An in-process admission gate caps that:

  • At most four writes per channel are in flight in one process.
  • Further writers wait in memory for up to two seconds, then get a retryable "service unavailable" answer.
  • A five-second lock timeout covers a writer that stalls while holding the counter.

Admission is per process, not across processes. Other message parents (documents, emails and so on) run no extra statement.

Who writes through it

Everything that changes a channel timeline: people's messages, reactions and threads, plus bots, calls, the agent harness, the Slack integration, document activity and imports. This is why the diff touches many backend crates.

Retention

Log rows older than thirty days are pruned hourly, in bounded batches. Counters are kept, so numbers are never reused. A device asking from before the oldest kept row is told to reset.

Layer 2: GraphQL reads

Four fields on the signed-in user, all backed by the existing message service and its permission checks:

FieldReturns
channelTimelineOne page of root messages and timeline activities, with cursors for before, after or around a point, and the channel's sequence at read time.
channelThreadOne bounded page of a thread's replies.
channelChangesThe changes after a given sequence, at most 200 per page, including deletions and the root of each changed reply. It sets resetRequired when the device is more than 1,000 changes behind or past retention.
channelMessageOne message, used when jumping to a location.
  • Sequence first, then the page. The server reads the channel's sequence before loading the page, so replaying from that number cannot skip a write that raced the read.
  • Same data as REST. Timestamps keep microseconds and optional fields are formatted as the REST API formats them. The pull request compared both APIs row for row on channels of 38, 1,490 and 5,950 rows.
  • Stable order. Each row carries a sort key the device can order by; message ids break ties at equal times.

Layer 3: the cache engine

The device cache already stored records and query results, but it had no order over messages and did not know which parts of a channel it held. The engine now keeps, per channel and per thread:

  • An index of message keys by sort key.
  • Covered ranges: stretches known to be complete. Fetching a page merges its range in, so adjacent pages join into one range and a jump to an old message leaves a separate island.
  • The sequence the channel is held at. It advances only from the value the caller read, so two tabs cannot skip a change between them.
channelTimeline(channel, thread?, limit, before | after | around)
  -> page: keys, cursors, sequence, whether the window is covered
  -> or "unsupported" (an older native build)
channelTimelineCommit(channel, coverage, removed keys, sequence, reset?)
channelTimelineEvict(not touched since, max channels)

The rule that keeps it honest: a read is answered from the device only when the whole requested window lies inside one covered range. Anything else is a miss, and the caller fetches. A reset drops coverage but keeps the records.

Storage: this is storage schema 13. It is a cutover, not a migration: browsers open a fresh database, and native apps replace the older cache along with any mutations still queued in it. Native binaries must be rebuilt to gain the new tables and commands, which is why #10441 fails the iOS and Android native checks until the version bumps are made. An older native build answers "unsupported" and keeps reading over REST.

Layer 4: how a channel opens and stays current

Opening, paging and jumping

Ask the deviceIf the window is held and covered, the channel renders with no request.
On a miss, ask GraphQLThe page is shown, then its rows, its range and the sequence are committed to the device.
If GraphQL fails, use RESTThe existing read, unchanged.

Opening never waits on the device. While the cache is still starting (a second or two on a new page), and for the latest page of a channel not yet known to be held, the server is asked at the same time and the first answer shows. The existing view model, page shape and cursors are unchanged.

Staying current

A push arrives for an open channelThe open view is patched directly from the push, as today. Nothing is refetched.
The device takes the same change by sequenceOne channelChanges(after held sequence) request commits the delta. Pushes that arrive while one is being stored share the next request.
Reconnect or reopenThe same request, from the sequence the device holds. Nothing changed means an empty answer.
Too far behindresetRequired: coverage is dropped and the latest page is fetched fresh.

The device takes a push a moment after the screen does. So a device page that is older than a push already on screen waits for that push to be stored and is read again, at most three times. A push not stored within two seconds is not waited on further.

Prewarm and eviction

  • Prewarm: while the person leaves the app alone, the latest page of up to forty unread and twenty recent channels is loaded, one request at a time. It stops without a connection.
  • Eviction: channels not opened for thirty days are removed from the device.

Offline

Timeline and thread queries run "offline first", so a held channel opens without a connection. A channel lookup that got no response decides nothing: the cached copy opens the channel, however many newer channels the person has. A read the device cannot serve offline waits for the connection without using up its retry.

Layer 5: writes that survive an outage

send / edit / delete / react
  -> the optimistic row on screen, as before
  -> device queue: optimistic cached row + a durable mutation
       online   -> sent over GraphQL; the returned row replaces the optimistic one
       offline  -> stays queued, survives a reload, delivered in order on reconnect
       busy     -> "service unavailable": retried with backoff, never counted as a failure
       refused  -> rolled back, with the usual toast and draft restore
  • No double posts. A send's identity in the queue is the message id the client minted. If the answer is lost and the send is replayed, the server returns the stored message for that id. A repeated delete returns the tombstone. Edits and reactions were already repeatable.
  • Long outages. A first delivery accepts an id minted up to thirty days ago, so a message typed during a long outage still posts.
  • Order. A queued send is placed past every message the server has positioned, never by the device's clock, so quick sends stay in the order written. When its delivery arrives, the message moves to where the server's time puts it.
  • Other windows. A write still queued after a second is announced to the device's other windows, which read the device again to show it. Such a message carries a "Not sent yet" mark.
  • What stays on REST. Anchored posts, other message parents, agents, bots and API tokens.

The message hooks keep their optimistic rows, toasts and rollback. Only the function that performs the write is swapped.

Reload safety: the three notes in local storage

The device cache runs in a worker and answers some milliseconds after the screen shows something, or a second or two later on a fresh page. A reload inside that gap would lose what the person just saw. Three small synchronous notes close the gap. Each is written first, forgotten once the device holds the thing, and picked up by the next page to start.

NoteCoversThe next page does
Unqueued sendsA send handed to the queue but not yet stored by it.Resends what the closed page left, in the order written.
Unstored pushesA push that reached the screen before the device stored it.Catches up those channels at start and after reconnect.
Unheld readsA latest page or thread the server answered before the device held it.Has the device hold them, so they open offline.

Two related repairs: if the cache storage is reset under an open page, the open channels' pages and threads are read again; and the queue releases a claim on its first write when the page that claimed it is gone, instead of waiting five minutes for the claim to lapse.

What the flag covers, and what it does not

The flag is enable-channel-local-sync. It exists in PostHog, on for company accounts and off for everyone else. A local or CI build sets VITE_ENABLE_CHANNEL_LOCAL_SYNC instead, which wins over PostHog. A change takes effect at the next reload.

GatedEverything the web app does with channels

One function, channelCacheHost(), returns nothing when the flag is off, and every caller then takes the existing REST path.

  • Device reads, catch-up, prewarm, eviction
  • Queued writes for send, edit, delete, react
  • The "Not sent yet" mark and other-window updates

Not gatedRuns for everyone once deployed

  • The backend. There is no backend flag. Every channel write bumps the counter and appends to the log.
  • Shared web code: the mutation queue runner (also used by email drafts), the GraphQL mutation retry helper, the query gate, the calendar GraphQL network file, and the channel detail lookup.
  • The cache engine build and storage schema 13.
  • Native code, which needs the version bumps.
Turning the flag off stops clients from using B. It does not undo the server write path. That needs a revert or a backend switch of its own, which is not built.

Writes already waiting when the flag goes off are not lost. Writes in the device queue are still delivered, because the cache runs its queue regardless of this flag. Sends that were only noted in local storage are posted over REST under their own id at the next page start.
