# Collaborative markdown editor fuzzer

Several people type into one document at once, each in a separate browser page,
through the real editor: `registerMarkdownEditing`'s plugins, `CollabProvider`,
the sync engine, the Loro mirror, and reconcile. Only the menus and drop
overlays are left out (they need the whole app's providers). The sync service
is played by the Playwright process (`relay.ts`): every update and awareness
message goes through it, and a peer can go offline and come back.

Each person types only at the end of their own region (the blocks after their
`Peer X:` marker), so `model.ts` predicts that region exactly from the
keystrokes: typing, Enter, Shift+Enter, Backspace, markdown shortcuts
(`# `, `## `, `### `, `> `, `- `, `1. `, and ```` ``` ```` then Enter). After
every keystroke the caret must be at the end of the model's current block.
After everything is delivered:

- every copy of the document, and the server's, are the same Loro state;
- every region matches its model, on every peer;
- the editor's internal markdown equals the markdown of its Loro document and
  of the server's (`toMarkdownText` in lexical-service);
- internal markdown survives an import and export unchanged;
- the editor state and its Loro document hold the same JSON;
- tree invariants hold (ids present and unique, lists hold list items) and no
  `console.error`.

## How it works

The input is generated by [fast-check](https://fast-check.dev), so a failure
shrinks to a short script and replays from its seed:

- `commands.ts`: model-based commands (`fc.commands` run by
  `fc.asyncModelRun`). A command is one person pressing a key, going offline or
  online, or the relay delivering a few messages. Keys are weighted towards
  typing (`fc.oneof` with weights); a key the model can't predict at that point
  (a shortcut outside an empty paragraph, say) fails its precondition and is
  skipped.
- `relay.ts`: each peer has an `up` and a `down` FIFO queue, and every queued
  message is a task in fast-check's scheduler (`fc.scheduler()`). A deliver
  command lets the scheduler pick which queues move, so delivery order is part
  of the input and shrinks with it, while each queue stays in order.
- `bridge.ts`: the page/test contract. The page publishes `LexFuzzApi` as
  `window.lexFuzz`; the test exposes `FuzzWire` (the server's end of the
  socket) and reaches the page through a typed `JSHandle<LexFuzzApi>`. Nothing
  augments the app's `Window`.
- `fixture.tsx`: one peer's page. `oracles.ts`: the checks above.
  `harness.ts`: opening peers and pressing keys.

Page-side work (Lexical updates, Loro commits, pushes) still runs on real
time, so a replay is close to, but not always exactly, the original run.

## Running it

From `apps/web`, with the fixture's server on 3017 (`LEXICAL_FUZZ_PORT` moves
both):

```sh
bunx vite --config src/lib/core/component/LexicalMarkdown/fuzz/vite.config.ts
FUZZ_RUNS=3 FUZZ_PEERS=3 FUZZ_STEPS=150 bunx playwright test \
  --config src/lib/core/component/LexicalMarkdown/fuzz/playwright.config.ts fuzz.browser
```

| Variable | Default | Meaning |
| --- | --- | --- |
| `FUZZ_RUNS` | 3 | fast-check runs; each opens fresh pages |
| `FUZZ_PEERS` | 3 | people, up to 8 |
| `FUZZ_STEPS` | 150 | most commands per run |
| `FUZZ_MINUTES` | 15 | time budget, shrinking included; shrinking stops at it and reports the smallest failure so far |
| `FUZZ_SHRINK` | on | `0` reports the first failure without shrinking |
| `FUZZ_IGNORE` | none | comma-separated finding kinds to report without failing a run, so shrinking looks for something else |
| `FUZZ_SEED`, `FUZZ_PATH`, `FUZZ_REPLAY_PATH` | | replay a failure: the seed and path from its report, and the `replayPath` printed after its commands |
| `FUZZ_UNDO` | off | see below |
| `FUZZ_DEBUG` | off | print the pages' console |

Every invocation writes `reports/fuzz-<seed>.json`: the seed and path, and for
a failure the shrunk commands, the scheduler's delivery order, and the
findings. While hunting for new bugs, ignore the known ones:
`FUZZ_IGNORE=markdown-round-trip,editor-vs-server-markdown,lexical-cascade-guard`.

`FUZZ_UNDO=1` adds two phases after typing: everyone presses Ctrl+Z until all
their edits are gone, taking turns with one delivery after each press
(`FUZZ_UNDO=sequential`: one person at a time), and the document must be back
to the markers; then everyone redoes, and every region must match its model
again. Findings carry the phase they came from.

`regressions.browser.e2e.ts` keeps the bugs the fuzzer found as fixed
scenarios, delivering every message at once; run it with the same
configuration and `regressions` as the test filter.

## Known findings

These show up in most runs:

- `markdown-round-trip`: internal markdown drops empty paragraphs on import
  (`PRESERVE_LINES` writes them as a space line, and Lexical's importer then
  removes the paragraph as empty), and code blocks lose leading and trailing
  blank lines.
- `editor-vs-server-markdown`: with two or more empty paragraphs in a row the
  client's export (its `\n\n\n \n\n\n` fix, which misses overlapping runs) and
  lexical-service's (no fix) differ.
- `lexical-cascade-guard`: Lexical's cascade counter only resets on a commit
  that finds its queue empty, and a no-op update never commits; the markdown
  shortcut listener queues one per typed character, so about 100 characters
  typed in a row trip the guard, which drops the queued updates.
- Undo phase: with collaborators, undoing everything can leave a character or
  an empty paragraph from early on; after redo, a node's id differs between
  each editor and the Loro document (the document's copy can lose its `$`).

Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` when the bundled browser can't run
(NixOS). If Chromium aborts requests with `ERR_NETWORK_CHANGED` (containers
restarting on the host), run Playwright inside `unshare -rn` with a socat
bridge from the namespace's 127.0.0.1:3017 to the host's.
