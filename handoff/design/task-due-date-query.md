# Bounded first page for open tasks by assignee and due date

**Verdict: rewrite Soup’s task page selection.** No index on an existing table can seek directly into a viewer’s visible, open tasks for one assignee in due-date order. A maintained projection with that key would let the shared Soup builder limit the ordered, authorized rows before hydration. The matching flat web My tasks “Due soonest” query would use it too.

## What a bounded design requires

The existing assignee GIN index yields all assigned IDs without due-date order. Status and Due Date are separate `entity_properties` rows, live state and update ordering are on `"Document"`, and visibility is in `entity_access` plus channel/team membership. PostgreSQL cannot index that join as an expression. Even a due-only B-tree with a typed date can scan an arbitrarily long date-ordered prefix of other assignees, closed tasks or invisible tasks. The current JSON-to-`timestamptz` expression also uses a non-immutable cast. An index on raw JSON text would need a proven canonical encoding to compare instants correctly. [Property schema](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/crates/macro_db_client/migrations/20251030100000_init_properties_schema.sql:117) · [Existing property indexes](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/crates/macro_db_client/migrations/20260511131825_properties_performance.sql:14) · [DATE sort expression](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/crates/soup/src/outbound/pg_soup_repo/grouping.rs:34)

Checking authorization before the outer limit over a task-only index can still reject all 100k assigned tasks. Putting a hard candidate cap ahead of authorization can return an empty or short page while eligible rows exist later. Starting from the viewer’s grants has the same problem in reverse and can read all 40k to produce even an empty page. Assignment writes can grant direct edit access, but assignment does not prove that the current viewer holds a grant, especially for SDK calls naming someone else. The existing `source_items` projection orders by update time and carries no assignee, Status or Due Date. A per-source extension would have work proportional to the number of sources, and would need an enforced source budget or a different exact path to make that work bounded per call. [Assignment grants](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/crates/properties/src/outbound/permission_service.rs:201) · [Source projection](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/crates/macro_db_client/migrations/20261118161741_source_items.sql:44)

A viewer-keyed projection gives the required read bound. The following is the index for that design, conditional on approval of the projection and verification of sort compatibility. The proposed table has one row per authenticated viewer, assignee and live task, deduplicated across direct, channel, team and project-derived grants. Use text IDs matching existing document ordering, nullable typed `due_at timestamptz`, the document’s update timestamp, and an `is_open` flag derived from the exact three-option Status OR.

```sql
-- no-transaction
CREATE INDEX CONCURRENTLY task_viewer_due_open_idx
    ON public.task_viewer_due
    (viewer_id, assignee_id, due_at ASC NULLS LAST, task_updated_at DESC, task_id DESC)
    WHERE is_open AND due_at IS NOT NULL;
```

In the expanded flat reader, match the effective AST before source fetch and grant count. Require an initial, document-only page with a positive task subtype, one exact Assignees reference, the default three open Status IDs OR’d in any order, a positive `TASK` Due Date range, Due Date ascending, and no extra predicates. Emit the page from the projection using the authenticated viewer and assignee as equality keys, literal `is_open AND due_at IS NOT NULL`, the present typed bounds (`>= start`, `< end`), matching index order and `LIMIT page_size + 1`. Both one-sided ranges use the same index with the absent comparison omitted. Feed those keys into the existing `Combined` hydration. Require an authoritative projection in the reader’s snapshot. Assignment, Status, range eligibility, live state and access must be exact before the index returns rows. A later authoritative recheck may fail a request on an invariant violation, but cannot silently drop rows to fill a shorter page. Neither the 100k task count nor the 40k grant count drives this query. Empty intersections cost a range seek even if either set is large.

Retain the update and descending text-ID tiebreakers and the existing cursor encoding. The current sort key is epoch microseconds represented as a double. Confirm parity for old values and continuation pages before committing to the typed-date index order. Distinct extreme timestamps can collapse to one old double key, so their tiebreaking needs an explicit compatibility decision. An unfiltered Due Date sort includes undated tasks. Grouped pages, continuations, negated or empty date filters, extra facets and alternative Status sets fall outside this first-page design.

## Web path

Yes, for the same expanded, ungrouped first page with the same three open options and a matching due range. The SDK sends `POST /items/soup/ast`. The web’s `buildTaskQuery` produces the same predicates with a different AND order and sends its translatable flat query over GraphQL, with REST available for other shapes. The GraphQL property-sort resolver and REST both reach the same Soup property-query repository arm. Route on the normalized AST and sort, so neither client needs a new endpoint. Selecting “Due soonest” by itself sets the sort and does not add a due range. ## Production cost and verification

- The repository’s November 2026 tiers put `Document` and `entity_access` at **10–100M rows each**. There is no published production row count for `entity_properties` or its due-date subset in those sources. The seed had 10.01M documents, 2.25M grant rows and 3.08M property rows. Production is PG 14.22 on `db.m9g.8xlarge` with gp3, 12,000 IOPS and 500 MiB/s configured storage throughput. [Production tiers](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/.agents/skills/query-review/table-sizes.md:1) · [MacroDB config](~/.herdr/worktrees/macro/synoet-sdk-list-tasks-by-due-date/infra/stacks/macrodb/Pulumi.prod.yaml:6) · [Seed table sizes](/tmp/sdkq-review.EM54Lp/seed-proof-fresh.txt)
- The index entry count is the sum over live open dated tasks of **distinct visible viewers × distinct assignees**. Source counts and the document tier do not bound that product. With two text principal IDs at 25–45 bytes each, a 36-byte task ID, timestamps and B-tree overhead, budget roughly 120–180 bytes per entry before bloat. At 10M indexed rows that is about **1.1–1.7 GiB**, or **11–17 GiB** at 100M, excluding the heap, uniqueness index, temporary space and WAL. For a 150–250-byte projected heap row, two scan-equivalents at the full configured bandwidth are roughly **6–10 s at 10M heap rows** or **60–100 s at 100M** in scan I/O alone. Budget for minutes under load and measure separately from the backfill. Sort, validation, WAL, competing traffic and old snapshots can dominate, so there is no reliable elapsed-time estimate from the saved plans. A concurrent build takes `ShareUpdateExclusiveLock` and keeps normal reads and writes available. Use its own one-statement migration after the projection schema, review the build and its effect on deployed writers, and confirm validity before enabling reads. If interrupted, drop the invalid index concurrently before retry.
- Projection maintenance is the production risk. Assignee, due date, Status, update timestamp, subtype, trash and restore can change many rows for a single task. Grant and membership changes can change many tasks for one viewer. Each change can add heap and index writes, WAL, vacuum pressure and replica lag. Preserve deduplication and revocation in the same committed state as the source facts. A delayed or unaudited projection cannot authorize the bounded read.
- PG 14 has no B-tree skip scan. The proposed index has equality on both leading columns followed by the due range, so it needs none. A generic plan can prove the literal partial predicate even with bound viewer, assignee and dates. PG 14 can still choose selective probes, a bitmap and sort, or a different join order under skew or stale stats. Fence the limited index read from hydration and require an ordered B-tree range scan directly beneath the limit, with no broad residual access or Status filter. Check fresh and stale `EXPLAIN (ANALYZE, BUFFERS)` in both plan modes on the same 10M seed, using PG 14 and the 40k- and 100k-grant viewers, wide, narrow, one-sided and empty ranges, and a case where matching tasks are invisible. Compare IDs, order, lookahead and cursor output to the current query. The DSS pool config and dynamic transaction set no statement timeout in code, so the new read also needs a transaction-local statement timeout aligned with the caller deadline.
