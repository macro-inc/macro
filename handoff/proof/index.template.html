Routines: define the follow-up once, schedule copies with their own triggers

Three stacked PRs ⟨PRS⟩ · heads ⟨HEADS⟩ · base main 4a9b72f7282 · 2026-11-19

The case you asked for: a routine that sets up the same follow-up for every item it handles (a reminder for each notification, a check-in on each task that moves to review), where the follow-ups are identical and only their trigger and their item differ. A routine can now define that follow-up once, as a sub-routine with named inputs. Each run schedules copies of it from code: macro.routines.schedule('review_check_in', { trigger: { type: 'once', at }, inputs: { taskId }, key }). A copy stores only { sub_routine, inputs } and reads the steps from its parent when it runs, so editing the definition changes every copy that hasn't run. The drafter writes routines this way, and the editor shows and edits the definition and its copies.

// crates/routine_program/src/sub_routine.rs
pub fn copy_program(&self, copy: &SubRoutineCopy) -> Result<RoutineProgram, CopyError> {
    let definition = self
        .sub_routine(&copy.sub_routine)
        .ok_or_else(|| CopyError::UnknownSubRoutine(copy.sub_routine.clone()))?;
    Ok(RoutineProgram {
        steps: definition.steps.clone(),
        mcp_servers: definition.mcp_servers.clone(),
        single_agent_task: false,
        sdk: self.sdk.clone(),
        dangerously_operate_as_user: false,   // a copy never writes as its owner
        inputs: definition.given(&copy.inputs)?,
        sub_routines: self.sub_routines.clone(),
    })
}

Keep as my routine on a copy makes it standalone: one write copies the definition's steps, apps and the copy's input values out of the parent (with the parent's definitions, so its own code still type-checks), and from then on parent edits no longer reach it. A copy's page shows the parent's definition read-only, with a link to edit it there.

5. What each PR changes

Scheduler: definitions, copies, run-time resolution
  • routine_program: SubRoutineDefinition (name, title, typed inputs without values, steps, apps), program-level inputs, SubRoutineCopy and copy_program. At most 5 definitions and 12 inputs; the code-step budget of 40 counts definitions' code steps.
  • Type checking: in a routine with definitions, macro.routines.schedule takes each definition's name with that definition's inputs (one overload per name), and each definition's code gets a typed inputs. A wrong name or input fails the save, not a run. Outside such a routine the name type is never, so nothing can call it; a routine without definitions gets main's check file byte for byte.
  • POST /scheduled-actions/schedule (from a running step only): the run's parent, the name and inputs again (TypeScript lets extra fields through a variable), the owner's enable-sub-routines flag, the 50-active cap shared with other sub-routines, a key that updates the item's pending copy instead of adding one. 404 for a parent deleted mid-run, 409 for the cap or a key held by something else, 413 for an oversized body.
  • Runs: a copy's run reads its parent and runs its definition; a missing definition or incompatible inputs fail that run with the reason. The new unique partial index scheduled_action_child_ref_idx serves keyed lookups.
  • Detach (Keep as my routine), code upgrade of definitions' code, rewritten-code inheritance on detach, and the two-step deploy (section 6).
Drafter and SDK: draft later work per item as a definition
  • finding/later.md: a new routine that may have code, whose owner has the flag, is told to define per-item later work once in subRoutines and schedule one keyed once copy per item from a code step, with the rules the scheduler and the check hold a copy to. Work that repeats until something happens stays one routine on its schedule.
  • The draft hands the definitions back (DraftedRoutine::sub_routines), and a code problem inside one names it. A draft whose definitions differ from what the brief allowed or what was checked fails rather than handing back something the editor can't save.
  • SDK: routine options take subRoutines; macro.routines.schedule; README and the composing skill. The eval gains due-soon-reminders and review-check-later, whose run check saves the draft, fires it, reads the copies it made, checks each copy's input, key and time, runs each copy by hand and checks its reply names its task.
Web editor: show and edit definitions and copies
  • The editor keeps definitions and input values on every save path (drafts, create, update, autosave), shows drafted definitions under Sub-routines for review, places each code problem on its definition's step, and edits a definition's steps with the routine.
  • A copy's page resolves its definition from the parent and shows it read-only, with the copy's input values: “Runs ‘Check in on the task’ from Check in-review tasks. Each run uses the current definition.” A missing definition or incompatible inputs hide Run now.
  • Keep as my routine and Duplicate with their eligibility checks (named definition, matching inputs, no active run, connected apps), run start and stop notifications kept in the row caches, approval of rewritten definition code, and Delete naming the copies it removes.

10. Choices, and what changing each would take

  • Copies reference the definition (your choice). A copy stores the definition's name and its inputs and reads the steps at run time, so one edit reaches every pending copy. The cost: a copy can't run without its parent (deleting the parent deletes its copies, and a missing definition fails the run with the reason), and a copy's page needs the parent's read. Snapshots per copy, the old way, would undo both and lose the edit.
  • A copy's task in the SDK is { sub_routine, inputs } (open question: copy read shape, option 1, until you decide). Stored code that reads another routine's task and branches two ways stops type-checking after the deploy; the code upgrade rewrites it, or pauses a routine that writes as its owner, with the reason. Option 2, the API returning a copy's task as a program with the parent's steps resolved, keeps such code checking: a change to the scheduler's read shape and the editor, about a day. Option 3, saved code keeping the SDK it was checked with, is the general fix for every SDK widening and its own project.
  • One-time copies, keyed per item. A one-time copy stops counting toward the cap of 50 once it fires; a keyed reschedule updates the pending copy instead of adding one. Recurring copies would need the cap to count a switched-off or finished one as done.
  • The flag gates every write of the new shapes, so the deploy can roll back until the flag goes on; the drafter reads it once per draft that may have code.
  • No definition review at draft time beyond showing it. The editor shows the definitions and their code; a dry run that shows the copies a first run would make would need the harness to record schedule calls without making them.
  • Narrow drafter change. One guide file and the hand-back checks; sibling work on the drafter (icons, connectors) touches the same prompts.
